# Шаг 5: совместный доступ к персонажам

## Цель
Дать владельцу возможность приглашать других игроков и отдельно разрешать просмотр или изменение разделов персонажа. Сохранить героев, формат данных, игровые расчёты и личные предметы.

## 1. Завершить проверки предыдущего этапа
- Создать разрешённый вами временный обычный аккаунт и временные данные, не меняя ваших героев и прав администратора.
- Проверить отказ в административных действиях обычному аккаунту, блокировку уже открытой сессии и восстановление доступа после разблокировки.
- Проверить одновременное рассмотрение одного предложения: только одно решение должно сохраниться вместе с соответствующей записью журнала.
- Исправить выявленные нарушения до включения совместного доступа.

## 2. Управление доступом
- На странице персонажа добавить «Доступ»: участники, ожидающие приглашения, изменение прав и отзыв доступа.
- Для каждого раздела — основные сведения, характеристики, навыки и опыт, инвентарь, заметки, история — предоставить режимы «Нет доступа», «Просмотр», «Изменение». История доступна только для просмотра: записи игровых действий создаёт приложение.
- По умолчанию ничего не раскрывать; приглашение нельзя отправить без явно выбранных разрешений.
- Только владелец управляет приглашениями, правами и удалением персонажа. Администраторская роль сама по себе не открывает чужих героев.
- В списке разделить собственных героев и героев, которыми поделились; показать владельца и доступный режим.

## 3. Приглашения
- Приглашение существующего аккаунта по точному адресу почты, без открытого списка пользователей. Получатель принимает или отклоняет приглашение внутри приложения; почтовая рассылка в этот этап не входит.
- Приглашение по одноразовой ссылке: вход обязателен, права задаёт владелец, срок действия виден при создании. Предложенный срок по умолчанию — 7 дней.
- Перед принятием показывать владельца и предоставляемые права. Само открытие ссылки не предоставляет доступ.
- Владелец может отменить приглашение; использованные, отменённые и просроченные ссылки больше не работают.
- Заблокированные аккаунты не могут создавать или принимать приглашения и пользоваться ранее выданным доступом.

## 4. Работа с общим персонажем
- Скрывать закрытые разделы и их данные уже при получении с сервера, а не только кнопки и вкладки.
- В режиме просмотра убрать действия изменения, удаления, использования предметов и распределения опыта.
- Проверять права для связанных действий целиком: повышение навыка затрагивает характеристики, использование предмета — инвентарь и активные эффекты. Историю таких действий записывать автоматически с указанием участника.
- Не раскрывать закрытые разделы через боевые показатели, сравнение предметов, историю, копирование, экспорт или страницы отдельных предметов. Если для вычисления нужны закрытые данные, не показывать этот результат.
- Давать доступ к изображениям только предметов доступного инвентаря, не открывая остальные файлы владельца.
- После отзыва прав обновлять открытый экран и очищать закрытые данные. Уже скачанные изображения и экспортированные данные отозвать невозможно; существующие временные ссылки действуют до истечения срока.
- При одновременном изменении не перезаписывать чужие правки молча: сохранить несвязанные изменения либо показать конфликт и предложить обновить данные, сохранив введённое пользователем.

## Техническая реализация
- Проверено: персонаж хранится целиком в `characters.data`; действующие политики разрешают доступ владельцу, а `CharactersProvider` сохраняет полный JSON через `upsert`. Эти операции необходимо адаптировать для совместного доступа, не создавать вторую систему хранения персонажей.
- Добавить отдельные таблицы участников и приглашений с явными GRANT и RLS. Ссылки хранить как хеши криптографически случайных токенов; идентификатор персонажа использовать текстовый, как в существующей таблице.
- Чтение общих героев выполнять защищёнными `createServerFn`, возвращающими только разрешённые разделы. Не предоставлять участникам прямое чтение полного JSON через Data API.
- Изменения проводить через серверно авторизованные операции с разрешёнными полями, проверкой актуальной версии и атомарным сохранением. Проверять права заново при каждом действии; не доверять присланным владельцу, роли или разрешениям.
- Существующие чистые игровые функции остаются единственным источником расчётов. Сервер загружает актуальный полный персонаж для операции, применяет правила и отдаёт разрешённый результат.
- Обновить существующий `CharactersProvider`, каталог-копирование и все пути записи персонажа для согласованной проверки версии и прав. Создание, перенос из браузера и удаление остаются действиями владельца.
- Приватное хранилище изображений сохранить; доступ участника проверять по конкретному персонажу и предмету. Отмена доступа и блокировка должны прекращать выдачу новых ссылок.
- Все страницы совместной работы оставить под существующим входом, добавить собственные заголовки и описания новым страницам.

## Проверка результата
- Тесты каждого разрешения, скрытых данных, запрета изменения чужих разделов, смены владельца, удаления и управления участниками; проверка связанных игровых операций.
- Тесты приглашений: принятие, повторное использование, отмена, истечение срока и заблокированный аккаунт.
- Проверка в двух реальных сессиях: владелец приглашает, участник принимает, видит только выбранные разделы, вносит разрешённое изменение; владелец видит сохранённый результат после обновления страницы.
- Проверка прямого запроса в обход кнопок, одновременных изменений и отзыва доступа при открытом экране.
- Удалить временные проверочные данные и аккаунт; существующий каталог не заполнять. Обновить список задач и сообщить только подтверждённые результаты.

## Не входит в этот этап
Расширенный импорт/экспорт JSON, CSV, изображений и ZIP, ручные резервные копии и MCP — отдельные последующие задачи. Не менять игровые правила, дизайн и данные существующих персонажей.
